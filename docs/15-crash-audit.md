# 크래시 전수조사 (2026-09-29 · 1.0.1 출시 뒤)

> 사용자: *크래시 가능성이 있는 부분에 대해서 전수 조사를 한번 했으면 해.*
> 지금까지 **실기기 크래시 0건** (S8 ① · 1.0 · 1.0.1). 여기서는 컴파일도 실행도 못 하므로 **코드를 읽어 따졌다.**

## 어떻게 했나

앱 코드 약 1만 2천 9백 줄(40 파일)을 세 칸으로 나눠 따로 읽혔다. 각 칸이 낸 주장 가운데 **중요한 것은 세션이 코드를 다시 읽어 확인했다** (✔ 표시).

| 칸 | 본 것 |
|---|---|
| 편집기 (`App/Editor`) | NSRange · `textStorage` 속성 범위 · 한글 조합 · 비동기 뒤의 낡은 범위 · 재진입 |
| Core (`Packages/Core`) | 배열 · `String.Index` · 범위 `a..<b` · 음수 반복 · UTF-16 과 글자 수 · 끝없는 반복 · 깊은 재귀 |
| 화면 · 저장 · 검색 | 파일 I/O · SQLite 빈 값 · 웹뷰 사진 건네기 · 스레드 · `ForEach` 이름 겹침 · `Int(Double)` |

**먼저 드러나는 모양부터 셌다:** `try!` · `as!` · `fatalError` · `precondition` **0건**. 강제 풀기(`!`) 3곳 — 모두 바로 앞에서 비어 있지 않음을 본다 ✔.

## 결론

**평소 쓰는 길에서 증명되는 크래시는 없다.** 인덱스 · 범위를 쓰는 자리는 거의 모두 앞에서 막거나 잘라 낸다 — 세 칸이 모두
같은 말을 했다. 남은 것은 **드문 입력**(아주 큰 파일 · 아주 깊은 중첩)과 **한글 조합 중 글 바꾸기**, 그리고 크래시는 아니지만
**윈도 줄 끝 파일에서 글이 잘못 고쳐질 수 있는 자리** 하나다.

## 크래시는 아니지만 알아 둘 것

- **검색 색인이 안 내려받은 노트를 모두 내려받게 한다** — 색인이 노트를 읽을 때 iCloud 에 받기를 시킨다. 검색이 본문을 알려면
  필요한 일이지만, 큰 폴더면 데이터 · 배터리를 쓴다. **설계로 정할 일** (다음 판 후보).
- **아주 긴 노트(수 MB)** 는 글자마다 전체를 다시 훑는 자리가 있어 **느려질 수 있다** (앱이 멈춘 듯 보임 — 크래시 아님).
- **3초 지켜보기**가 드물게 방금 친 글자를 디스크 글로 덮을 틈이 있다(밀리초). 저장 뒤 다시 확인하도록 고칠 수 있다.

## 안전하다고 확인한 곳 (요약)

편집기의 `lineBeforeCaret` · 사진 줄 · 제목 줄 · 자리 잇기(176) · 목록 번호 · 들여쓰기 · 붙여넣기 범위 — 모두 길이로 자른다.
Core 의 `LineStyler` · `ListEditing` · `Formatting` · `NoteLinking` · `Paths` · `FrontMatter` · `LineMap` — 인덱스 앞에 검사, 반복은 늘 앞으로 간다.
SQLite — 빈 칸은 `""`, 닫힌 뒤 호출은 막힘, 문장은 `await` 를 건너지 않는다. 웹뷰 사진 건네기 — 멈춘 요청에 다시 안 보낸다.
