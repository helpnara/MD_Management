## 1. "1.0" 이 무엇인가

**1.0 (TestFlight, 나 혼자 · 내 기기들)** — 한 사람이 자기 폴더 안의 `.md` 파일을
아이폰 · 아이패드에서 **보고 · 고치고 · 찾는다.** 이미지 · 첨부는 마크다운 표준
링크로 그 자리에서 본다.

**2.0 (App Store 공개)** — 태그 · 백링크 · `[[wikilink]]` 이동 · 앱 잠금 · 위젯 ·
공유 확장 · PDF 내보내기. 1.0 에 넣지 않는다.

**만들지 않는 것 (1.0 · 2.0 공통)** — 다른 Apple ID 와 공유 · 외부 네트워크 · 계정 ·
서버 · 자체 파일 형식.

## 4. 앱 이름 — `느린 여백` (2026-09-13 확정)

`느린 부자의 기록` 과 한 가족 브랜드로 묶었다. 단독 `여백` 은 KIPRIS 에서 등록
상표가 확인돼 쓰지 않는다.

**이름은 코드의 두 곳에만 있다.** 바뀌면 이 두 줄과 문서를 고치면 된다:

| 자리 | 파일 | 값 |
|---|---|---|
| 스토어 · 홈 화면 이름 | `project.yml` → `CFBundleDisplayName` | `느린 여백` |
| `Files` 앱의 폴더 이름 | `project.yml` → `NSUbiquitousContainerName` | `느린 여백` |

**Xcode 타깃 · 스킴 이름(`Notebook`)과 번들 ID(`com.helpnara.markdown`)는 이름과
무관하게 고정**이다. 번들 ID 는 App Store 등록 후 바꿀 수 없으므로 일부러 이름을
안 넣었다.

**아이콘**은 `Tools/icon/icon-source.png` 를 `Tools/icon/bake-icon.py` 가 굽는다.
원본을 저장소에 두는 이유는 결과물만 있으면 나중에 손볼 수 없기 때문이다.

### T4 검토 — 개요가 두 단계에서 멈추는 까닭 (2026-09-15, 사용자 · 빌드 30 · 1 · 2번)

**정해서 그런 것이 아니라 막힌 것이다.** 한계를 두자고 정한 적이 없다.

- **글자는 계속 들어간다.** `ListEditing.indent` 는 깊이를 세지 않는다 — 탭을 누르는 만큼 빈칸 둘씩 붙는다.
- **파일도 맞다.** 읽기 모드(cmark-gfm)에 `- 첫째 /   - 둘째 /     - 셋째 /       - 넷째` 를 주면 네 단계가
  제대로 겹친다. 파이썬 심판으로도 확인했다.
- **막힌 것은 편집기의 칠하기다.** `LineStyler` 는 **문단 하나만** 본다(ADR-0005). 그 눈에는
  `    - 셋째` 가 **네 칸 들여쓴 코드 줄**이다 — CommonMark 가 정말 그렇게 읽는다. 목록인 줄을 알려면
  "앞 줄이 목록이었다" 는 문맥이 필요한데 그것이 없다. 그래서 셋째 단계부터:
  - 글꼴이 고정폭이 되고, 목록 들여쓰기(`nestStep * depth`)가 통째로 사라져 **왼쪽으로 튕겨 보인다**,
  - 줄바꿈이 다음 항목을 안 이어 준다 (`ListEditing.returnPressed` 가 코드 줄로 보고 물러난다).

**고치는 길 — 목록 마커가 네 칸 규칙을 이긴다.** `LineStyler.blockPrefix` 에서 네 칸 이상이면 코드로
보내기 **전에** 마커(`- ` · `* ` · `+ ` · `1. ` · `1) `)를 먼저 본다. 있으면 깊이에 상관없이 목록 줄이다.
깊이 계산(`depth = marker.start / 2`)과 매달린 들여쓰기는 이미 임의 깊이를 다루므로 그대로 산다.
`returnPressed` · `outdent` 도 따라서 풀린다.

**값:** 네 칸 들여쓴 **코드** 줄이 `- ` 로 시작하면 편집기는 목록으로, 읽기 모드는 코드로 그린다 —
둘이 어긋난다. 코드 울타리(` ``` `)는 따로 처리하므로 영향이 없고, 메모 앱에서 네 칸 코드 블록은
드물다. **겹친 개요가 훨씬 흔하다.**

**곁들일 것:** 탭(`\t`)으로 들여쓴 줄은 지금 `depth = marker.start / 2` 가 0으로 세어 한 단계도 안
들어간 것처럼 그린다. 같이 손본다.

**심판을 어떻게 세우나.** `style_facts` 는 한 줄만 markdown-it 에 준다 — 그러면 심판도 코드라고 답한다.
들여쓴 목록 줄은 **조상 항목을 앞에 붙여** 문맥째 물어 markdown-it 이 스스로 "겹친 항목" 이라고
답하게 한다. 그래야 기댓값을 손으로 적지 않는다.

**크기:** 반나절. Core 한 군데 · 심판 한 군데 · 골든 사례 몇 건.

### T2 검토 — `#ABC` 태그 (2026-09-15)

**된다. 마크다운과 부딪히지 않는다.** CommonMark 는 `#` 뒤에 **빈칸이 있어야** 제목으로 본다 — `#ABC` 는
제목이 아니라 그냥 글자다 (골든 케이스 `제목 아님 — 빈칸 없음` 이 이미 그것을 지킨다). 그러니 줄 첫머리의
`#ABC` 든 문장 가운데의 `#ABC` 든 태그로 칠해도 제목과 헷갈릴 일이 없다.

붙어야 할 자리는 넷이다.

1. **편집기** — `StyleToken` 에 `tag` 를 더하고 `LineStyler` 의 인라인 훑기에서 `#` + 낱말을 잡는다.
   마커가 아니라 **글자 전체**를 칠한다(L2 에서 숨기면 안 된다 — `#` 이 태그의 일부다).
   `EditorStyleSheet` 에 노란색. 골든 케이스로 규칙을 박는다 (`#태그`, `가운데#태그`, `#` 홀로, `# 제목` 은 아님).
2. **읽기 모드** — `swift-markdown` 은 태그를 모르므로 AST 의 글자 노드를 훑어 `<span class="tag">` 로 바꾼다.
   이미 AST 를 고치는 자리(`MarkdownHTML`)가 있어 그 옆에 붙는다.
3. **검색** — 색인의 `tags` 칼럼은 지금 **머리말의 `tags:`** 만 담는다. 본문의 `#ABC` 를 여기에 더하면
   `tag:ABC` 검색이 그대로 된다. 한 줄 늘어나는 정도다.
4. **문서** — 설계서 §5.1 의 태그 설명과 ADR 에 한 줄.

**주의할 것 둘.** ① 코드 블록 · 인라인 코드 안의 `#` 은 태그가 아니다 (`#include`). ② 한글 태그(`#기획`)를
받으려면 낱말 판정을 유니코드로 해야 한다 — 영문자만 보면 한글이 안 걸린다.

**규모:** Core 한 파일 · 앱 두 파일 · 골든 케이스 네댓. 하루치.
