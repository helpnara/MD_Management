### Description

```
Your writing stays as files.

Slow Margin opens the Markdown (.md) files in your iCloud folder and lets you read and edit them directly. Nothing is tucked away inside the app, so your notes are still there if you delete the app, move to another app, or come back years from now.

The same files show up in the Files app and on your Mac. If you already keep a folder of Markdown notes, just open it.

— Write without fighting the syntax

Only the line with the cursor shows its Markdown. Everything else looks the way it reads, so there’s no switching between edit and preview.

The toolbar above the keyboard has bold, italic, strikethrough, links, quotes, tables, and indent. Press Return in a list and the next item follows; use Tab to indent and outdent.

In Read mode, tap a checkbox to check it off. It’s saved to the note file without switching to editing.

— Photos and attachments stay with your notes

Photos from your library or camera go into an assets folder next to the note, with a link in the text. You can attach documents like PDFs too, and tap to open them.

— Link your notes

Type [[ and pick a note by title. If the title doesn’t exist yet, a new note is created and linked. Files keep standard Markdown links only.

At the bottom of Read mode you’ll find the notes that link to the one you’re reading. Tap to jump there.

There’s also a place that gathers every link that doesn’t open.

— Paste, and it fits

Paste a web address and it becomes a link. Copy a table and it becomes a Markdown table. Paste a list onto lines you’ve already numbered, and the numbers won’t double up.

— Send from other apps

Choose Slow Margin in another app’s share menu to send text, web links, or photos. Open the app and they arrive as new notes in your Inbox folder.

— Search

Search titles and text at once, starting from two characters.

— No account

No sign-up. No server. No ads or tracking. Your writing lives only on your device and in your iCloud, and not even the developer can see it.

— iPhone and iPad

One app for both. On iPad, folders, notes, and the editor sit side by side, with keyboard shortcuts for a hardware keyboard.

주요 기능:
- 마크다운 파일을 그대로 열어 읽고 고칩니다. 커서가 있는 줄만 원문으로 보입니다.
- 사진과 문서를 노트 옆 assets 폴더에 넣고 본문에 링크합니다.
- 노트 제목으로 다른 노트를 찾아 링크합니다.
- 본문과 제목을 함께 검색합니다.
```

> **기능 목록을 넣어 둔 까닭.** 메모 앱은 *기능이 너무 단순하다*(4.2)로 걸리는 일이 있다.
> 무엇을 하는 앱인지 심사자가 한눈에 보게 적어 둔다.

### 두 주장을 코드로 확인했다 (2026-09-24)

심사자는 이 글을 **그대로 따라 한다.** 그래서 적어 둔 것이 맞는지 봤다.

| 메모가 말하는 것 | 코드 | 맞나 |
|---|---|---|
| 앱 전용 iCloud 폴더가 만들어진다 | `FolderSource.iCloudDocuments()` 가 컨테이너의 `Documents` 를 만든다 | ✅ |
| 견본 노트가 **한 개** 들어간다 | `seedIfNeeded` 가 `첫 노트.md` 하나를 쓴다. 이미 쓰던 폴더에는 안 넣는다 | ✅ |

### ✅ 아이클라우드가 없는 심사 기기 — 메모 한 문장으로 막았다 (2026-09-24)

`iCloudDocuments` 가 `nil` 이면 **기기 안 폴더**로 물러난다. 그 길에는
`seedIfNeeded` 가 없다 — **빈 목록**이 뜬다. 심사자 기기에 iCloud Drive 가 꺼져 있으면
*앱이 아무것도 안 한다* 로 읽힐 수 있다 (2.1).

**고치는 길 둘.**

| | 값 |
|---|---|
| 심사 메모에 **한 문장**을 더한다 | 지금 할 수 있다. 붙여넣기 한 번 |
| 기기 안 폴더에도 첫 노트를 둔다 | 빌드가 한 바퀴 더 든다. **S8 을 되감는다** |

**메모에 한 문장을 더하는 쪽**이 값이 맞다. ✅ **붙였다** (2026-09-24 사용자).
아래가 심사 메모 끝에 붙은 글이다:

```
기기에 iCloud Drive 가 꺼져 있으면 앱은 기기 안 폴더를 쓰고 목록이 비어 있습니다.
오른쪽 위 연필 단추로 새 노트를 만들거나, 설정에서 다른 폴더를 고르시면 됩니다.
```

## 6. 업데이트 판 내기 — 매번 이 순서 (2026-09-28 사용자 요청으로 정리)

> 1.0 이 나간 뒤의 판(1.0.1 · 1.0.2 · 1.1 …)은 모두 이 길로 간다. **첫 제출과 다른 점**: 스크린샷 · 설명 · 설문 ·
> 처리방침은 **지난 판에서 그대로 따라온다** — 바꿀 것만 바꾼다. 새로 적는 칸은 *이 버전의 새로운 기능* 하나다.

| 단계 | 누가 | 무엇 |
|---|---|---|
| **1. 모으기** | 사용자 → 세션 | 쓰다가 찾은 것을 번호로 쌓는다 (`08-feedback.md`). 5개 내외면 세션이 *착수할까요?* |
| **2. 만들기** | 세션 | *착수하자* → 코드 · 정답표 · CI 초록. **버전 번호**를 `project.yml` 의 `MARKETING_VERSION` 에서 올린다 (아래 규칙) |
| **3. TestFlight** | 세션 | `testflight.yml` 을 돌린다. **빌드 번호 = 그 실행 번호** (57, 58 …). 10~15분 뒤 TestFlight 앱에 뜬다 |
| **4. 확인** | 사용자 | TestFlight 앱에서 설치 — **앱 스토어판 위에 덮어쓴다. 노트는 iCloud 폴더에 그대로.** 확인 목록 1~n → *확인 완료* |
| 4′. 고칠 것 | 세션 | 걸리면 같은 버전으로 다시 올린다 (빌드 58 · 59 …). **심사에 내기 전까지는 버전을 안 올린다** |
| **5. 새로운 기능 글** | 세션 → 사용자 | 세션이 초안을 쓰고 `Tools/store/count.py` 로 센다 (한도 4000자). 다른 앱 이름 · 없는 기능 금지 (CLAUDE.md §6) |
| **6. 제출** | 사용자 | App Store Connect → 앱 → **iOS 앱** 옆 **+** → 버전 번호(예 `1.0.1`) → *이 버전의 새로운 기능* 붙이기 → **빌드** 칸에서 확인한 빌드 고르기 → 출시 방식 고르기 → **심사에 제출** |
| **7. 심사** | 애플 | 업데이트는 보통 **하루 안팎.** 결과는 메일. 반려면 사유를 §5 처럼 여기 적고 대응 |
| **8. 출시** | 사용자 | **수동 출시**를 골랐으면 *개발자 출시 대기* → **이 버전 출시** (1.0 때와 같다). 자동을 골랐으면 승인 즉시 |
| **9. 받기** | 사용자 | 앱 스토어 → 프로필 → 업데이트 (자동 업데이트가 켜져 있으면 저절로). TestFlight 판을 쓰던 기기도 여기서 정식판으로 돌아온다 |
| **10. 다음 판 준비** | 세션 | 승인된 버전은 **닫힌다** — 같은 번호로는 TestFlight 에 더 못 올린다. 다음 착수 때 버전을 또 올린다 |

**버전 번호 규칙.** 고침 · 작은 편의는 `1.0.x`, 눈에 띄는 기능 묶음은 `1.x`. 빌드 번호는 신경 쓰지 않는다 — CI 가 매긴다.

**빌드를 고를 때 암호화 질문**이 나오면: `ITSAppUsesNonExemptEncryption = false` 를 이미 넣어 두어 보통은 안 묻는다.
물으면 *암호화 안 씀* (네트워크를 안 쓰는 앱이다).

**출시 방식 — 업데이트는 자동을 권한다** (2026-09-28 사용자 질문으로 정리).

| 고를 것 | 뜻 | 언제 |
|---|---|---|
| **이 버전 자동 출시** (권함) | 승인되는 순간 나간다 | 고침이 든 판 — 기다릴 까닭이 없다. 이미 TestFlight 에서 확인했다 |
| 이 버전 수동 출시 | 승인 뒤 *개발자 출시 대기* — 내가 **이 버전 출시**를 눌러야 나간다 (1.0 이 이랬다) | 블로그 · 소식과 **나가는 시각을 맞추고** 싶을 때 |
| 날짜 지정 자동 출시 | 정한 날짜 **이후** 승인되면 그때 나간다 | 날짜가 정해진 행사가 있을 때. 심사가 늦으면 그 날짜를 넘긴다 |

**단계적 출시**(7일에 걸쳐 자동 업데이트를 늘리는 것)는 **끈다** — 쓰는 사람이 적은 지금은 이득이 없고, 고친 판이 늦게 퍼진다.

**얼마나 자주 내나 (2026-10-02 사용자 결정 — *너무 자주 업데이트해서 심사하는데 불이익이 생길 수도 있어?*).**
자주 낸다고 심사에서 불이익을 받지는 않는다 — 애플은 횟수를 제한하지 않고 판마다 따로 본다 (공개된 관행 기준, 문서를 다시 확인한 것은 아니다).
실제 비용은 따로 있다:

| 비용 | 어떻게 다루나 |
|---|---|
| 판마다 심사를 기다린다 (보통 하루 안팎). 앞 판이 심사 중이면 다음 판을 못 낸다 | **고치고 확인하는 일은 TestFlight 에서**, 앱 스토어에는 확인이 끝난 묶음만 낸다 |
| 심사 중인 판을 빼면 기다림이 처음부터 다시 시작된다 | 급하지 않은 것은 빼지 않고 **다음 판에** 싣는다 |
| 내용 없는 판이 잦으면 심사에서 물어볼 수 있다 | *새로운 기능* 글은 **실제로 바뀐 것만** 적는다 (CLAUDE.md §6) |
| 업데이트 알림이 잦다 | 앱 스토어 판은 **1~2주에 한 번** 정도로 모은다 |
| 평점 | 새 판을 낼 때 **평점 요약 초기화를 고르지 않는다** |

**예외 — 바로 낸다:** 자료가 사라지거나 저장이 안 되는 문제, 앱이 꺼지는 문제 (CLAUDE.md §3 과 같은 예외).
1.0 → 1.0.4 를 일주일에 다섯 판 낸 것은 출시 직후라 자연스러웠다. 이제부터는 위 간격으로 간다.
